# Two duration ablation hypotheses and adaptive-width gate audit

Read-only inspection, 2026-10-07. No observer edits or new judge executions. Scores remain unproven for both proposed settings.

1. **`PRO_LAMBDA_FRAC=.60` versus default `.45`, all other settings fixed.** `planner.py` computes `lambda_frac=LAMBDA_FRAC*min(1,max(.2,scarcity/.86)^SCARCITY_POWER)` (default power1), then `lam=lambda_frac*rate_ema`, and field net value `gain-lam*actual_duration`. A higher fraction favors shorter duration for fixed field/gain/time-price state. Test whether it reduces the observed saturation excess without increasing retrospective replacement or losing science. EMA feedback and cross-field selection mean this is not a monotonic score claim. Lower lambda has already regressed in prior tests and is not proposed again.
2. **`PRO_KAPPA=1.3` versus default `1.0`, separately.** The actual shaping is `top_multiplier*(score_per_weight/top_multiplier)^KAPPA`, with marginal difference against current best. A normalized half-completion falls from .5 to .406; saturation remains1. This suppresses new partial exposures but increases the attractiveness of finishing already-partial targets. It may reduce later replacement while increasing shared exposure length and bright-target saturation. KAPPA2 previously regressed; mild shaping is only a bounded new hypothesis.

Compare official science/total/components and CPU, plus occupied fiber-time, saturation excess, final nonrepresentative fiber-time, occupancy, and durations. RC1 previously had 549.897 saturated fiber-hours and 425.542 final nonrepresentative fiber-hours, union973.102. RC2 reduced nonrepresentative time20.542h but increased saturation36.988h, gaining only21.716 science; these losses cannot be optimized independently.

Bright targets stop adding marginal gain after `reach=min(1,flux*T*model*scale/450)` saturates, yet remain assigned during a shared exposure. Longer duration can therefore remain preferable because faint targets' aggregate marginal utility exceeds the telescope-time price. Season multipliers change that utility and use full replacement costs; they do not independently release saturated fibers during an action. This is a joint-field tradeoff rather than proof of a duration bug.

## Deep-search gate

**Confirmed code fact; performance impact plausible:** `agent.py:_pace` compares `deep_ema[0]` and `deep_ema[1]`, measured as total CPU/wall of earlier deep turns at their selected width, against current per-decision budgets. It does not normalize those deep costs to width1. Width itself is subsequently selected from `search_base_cpu_ema`, which *is* normalized by effective width after the RC3 fix. A historically expensive wide search can therefore disable deep search even when a narrower deep search is predicted to fit. The default 1.2 hysteresis and 0.85 decay every50 inactive decisions make the gate deliberately conservative, but also retain stale width-dependent cost.

The current RC3 decision log demonstrates the conditions, not the counterfactual score: early steps2–20 run effective widths6.33 down4.13 at roughly.78–1.01 process seconds/turn. Step144 requests1.884 but runs effective1, level0, process.2009sec; steps135–155 stay effective1 despite requested widths~1.57–2.04, while remaining normalized CPU is still~810sec. Width scaling is not exactly linear, and field density and weather change, so these observations do not prove narrower deep search would improve score or safely match the prediction.

A minimal experiment within existing pacing logic would store *separate width-normalized deep CPU and wall EMAs* at measurement, retaining the existing total-cost EMAs for diagnostics. Gate whether width1 deep effort fits; retain the absolute deadline, reserve, width cap, existing level gate, and hysteresis. Width remains chosen separately and deadline bounded. This avoids treating an earlier width10 cost as the minimum deep cost. No change is implemented here; require a regression with a wide expensive prior deep turn and a feasible narrower allowance, plus fallback/reserve tests and matched CPU/score evidence before promotion.
